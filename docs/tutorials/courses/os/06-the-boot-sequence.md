# Lesson 06 — Understand the Boot Sequence

**Goal:** trace the handoff from the virtual machine to the VNT kernel.

## 1. Startup has stages

When you run QEMU with `-cdrom build/vntos.iso`, QEMU creates a virtual x86 machine and presents the ISO as boot media. Firmware starts the boot process, GRUB loads the kernel ELF according to its configuration, and GRUB transfers control to the kernel's Multiboot2 entry point.

The kernel cannot immediately assume that the CPU is in the mode its compiler expects. The bootstrap initializes the minimum CPU state required by the compiled 64-bit kernel.

## 2. The VNTOS path

The current intended path is:

```text
QEMU virtual machine
  → firmware / GRUB
  → Multiboot2 kernel entry (boot32_entry)
  → create initial page tables
  → enable long mode and paging
  → long_mode_entry
  → call _start (generated by the freestanding backend)
  → kernel_main()
  → initialize serial output
  → print prompt and handle commands
```

Read this as a sequence of handoffs, not a list of independent features.

## 3. Entry points matter

The linker script declares `boot32_entry` as the ELF entry. This is the early assembly entry point, not the VNT function `kernel_main`. Later, `long_mode_entry` calls `_start`, which is emitted by the freestanding compiler backend and eventually invokes the kernel's main function.

If you jump straight to `kernel_main`, you miss the work needed to make it safe for the CPU to execute that code.

## 4. Debug output during boot

The bootstrap writes a few marker bytes to the QEMU debug port `0xE9`. Those writes are early diagnostic breadcrumbs in the assembly. They are not the normal user-facing serial shell and should not be confused with COM1 serial output.

The kernel later initializes COM1 and prints readable text to the serial console. Keeping the two paths distinct helps when debugging a failure that occurs before the serial driver starts.

## 5. What information crosses the handoff?

A boot protocol can pass information such as memory maps or boot-device details. The current bootstrap shown in `os/boot.S` does not implement a complete Multiboot2 information parser. Do not assume VNTOS currently uses a bootloader-provided memory map simply because it uses Multiboot2.

This matters: a real memory manager must learn which physical memory is usable and which regions are reserved before allocating pages.

## 6. Boot is a sequence of contracts

Every stage must establish the conditions required by the next stage. GRUB must recognize the Multiboot2 header and load the ELF segments. The bootstrap must establish a stack and the page tables needed to execute 64-bit code. The long-mode transition must configure the CPU correctly before control reaches compiled VNT code. The kernel entry must initialize the console before relying on user-visible diagnostics.

This is best understood as a chain of contracts. If a stage fails to meet its contract, later code may never run. For example, adding a debug print to VNT cannot diagnose a fault that occurs before the VNT entry point is reached. Early failures need an earlier observation method, such as a boot marker or QEMU's debugger.

## 7. Build a timeline from source

Open `os/boot.S` and `os/kernel.vnt`. Mark the exact labels and functions that form the handoff. Then find the point where the interrupt subsystem is initialized and the point where the shell begins accepting commands. Do not infer the order from filenames; trace the calls and branches.

Your timeline should distinguish at least these events:

1. GRUB selects and loads the kernel ELF.
2. The Multiboot entry begins in the bootstrap's initial CPU mode.
3. The bootstrap establishes page tables and the stack.
4. The processor enters long mode and jumps to the kernel entry.
5. VNT code initializes output and device helpers.
6. The IDT/PIC/PIT path is initialized before maskable IRQs are enabled.
7. The shell enters its command loop.

If the current source changes, update your timeline from the code.

## 8. The handoff is not a normal function call

The bootloader does not call `kernel_main` using the C or VNT calling convention. It transfers control according to the boot protocol. The bootstrap must therefore establish any CPU state and stack assumptions required by the compiled entry code. Treat the bootloader-provided registers as protocol data, not as arbitrary function parameters.

Similarly, an interrupt does not use the ordinary function-return path. Its entry and exit convention is handled separately in the later interrupt lessons.

## Lab: diagnose a missing marker

Imagine that the build completes but the expected boot marker never appears. List the earliest possible stage where execution could have stopped. For each stage, name an independent observation: artifact existence, ELF headers, GRUB output, a bootstrap marker, serial initialization, or a QEMU debugger breakpoint. Your diagnosis should narrow the stage before proposing a source edit.

## 9. Compare the expected and observed timeline

Keep two timelines: one derived from source and one derived from runtime evidence. The source timeline tells you what should happen; the observed timeline records the last marker actually seen. A difference between the two identifies the stage to investigate.

For example, if the serial banner appears but the shell prompt does not, the bootstrap and at least part of console initialization succeeded. Investigate the path between the banner and the shell loop before revisiting GRUB or long-mode setup. If no serial output appears, first verify the QEMU serial routing before concluding that the CPU never reached the kernel.
