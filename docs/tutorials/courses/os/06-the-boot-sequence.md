# Lesson 06 — Understand the Boot Sequence

**Goal:** trace the handoff from the virtual machine to the VNT kernel.

## 1. Startup has stages

When you run QEMU with `-cdrom build/vntos.iso`, QEMU creates a virtual x86 machine and presents the ISO as boot media. Firmware starts the boot process, GRUB loads the kernel ELF according to its configuration, and GRUB transfers control to the kernel's Multiboot2 entry point.

The kernel cannot immediately assume that the CPU is in the mode its compiler expects. The bootstrap initializes the minimum CPU state required by the compiled 64-bit kernel.

## 2. The VNTOS path

The current intended path is:

```text
QEMU virtual machine
  → firmware / GRUB
  → Multiboot2 kernel entry (boot32_entry)
  → create initial page tables
  → enable long mode and paging
  → long_mode_entry
  → call _start (generated by the freestanding backend)
  → kernel_main()
  → initialize serial output
  → print prompt and handle commands
```

Read this as a sequence of handoffs, not a list of independent features.

## 3. Entry points matter

The linker script declares `boot32_entry` as the ELF entry. This is the early assembly entry point, not the VNT function `kernel_main`. Later, `long_mode_entry` calls `_start`, which is emitted by the freestanding compiler backend and eventually invokes the kernel's main function.

If you jump straight to `kernel_main`, you miss the work needed to make it safe for the CPU to execute that code.

## 4. Debug output during boot

The bootstrap writes a few marker bytes to the QEMU debug port `0xE9`. Those writes are early diagnostic breadcrumbs in the assembly. They are not the normal user-facing serial shell and should not be confused with COM1 serial output.

The kernel later initializes COM1 and prints readable text to the serial console. Keeping the two paths distinct helps when debugging a failure that occurs before the serial driver starts.

## 5. What information crosses the handoff?

A boot protocol can pass information such as memory maps or boot-device details. The current bootstrap shown in `os/boot.S` does not implement a complete Multiboot2 information parser. Do not assume VNTOS currently uses a bootloader-provided memory map simply because it uses Multiboot2.

This matters: a real memory manager must learn which physical memory is usable and which regions are reserved before allocating pages.
