# Lesson 12 — Hosted Programs Versus Freestanding Kernel Code

**Goal:** understand why compiling VNT for a kernel is different from compiling an ordinary VNT program.

## 1. A hosted program

A normal VNT executable is built to run under an existing operating system. It can link against VNT's native runtime and use services provided by Windows or a Unix-like system. That environment supplies process startup, memory management, file access, and many other facilities.

A kernel is the environment that normally provides those facilities to other programs. It cannot call its own host operating system to get them before the kernel exists.

## 2. Freestanding means fewer assumptions

The build script uses the compiler's freestanding mode to emit assembly for `os/kernel.vnt`. That root imports `serial.vnt`, `console.vnt`, `ps2.vnt`, and `interrupts.vnt`; the compiler loads their declarations into the same freestanding compilation unit. The generated VNT assembly is then assembled and linked without a hosted C runtime. The kernel needs a defined entry point and must avoid depending on hosted APIs that are unavailable at boot.

The freestanding backend currently supports a restricted subset of VNT. It does not imply that every standard-library module or hosted language feature works in the kernel. Check the current compiler documentation and tests before relying on a feature.

## 3. Entry and function flow

The linker enters at `boot32_entry`, then the assembly eventually calls the generated `_start`. The freestanding backend emits the startup glue that reaches `kernel_main`.

This is why `kernel_main` is not the ELF entry point. It is the main kernel function after the CPU bootstrap and generated entry code have run.

## 4. Inline assembly is a sharp tool

The current kernel uses inline assembly for:
- UART port I/O;
- CPU halt and reboot control;
- reading linker-defined symbol addresses;
- a few operations that rely on the compiler's current stack-frame layout.

These are implementation constraints, not ideal long-term interfaces. Hard-coded stack offsets are especially brittle: a compiler optimization or calling-convention change could move a local variable. Proper VNT intrinsics or small, well-defined compiler-supported primitives would be safer than depending on incidental stack layout.

Do not blindly copy the inline assembly into another function. Before modifying it, inspect the generated assembly and understand the exact calling convention.

## 5. Why interrupts have one small external assembly file

VNT's current inline-assembly feature has no operand constraints or clobber list. Interrupt entry must preserve every interrupted register, account for exception-specific error-code pushes, align the stack before calling compiled code, and return with `iretq`. Hiding that ABI inside an ordinary VNT function would be unsafe. `os/interrupts.S` keeps those CPU mechanics in one auditable file; `os/interrupts.vnt` contains the event policy and diagnostics.

This is not an excuse to move the rest of the kernel into assembly. Serial, VGA, PS/2, shell, and interrupt policy live in VNT files.

## 6. What the kernel currently lacks

The current kernel is not linked with a hosted runtime, and it does not yet have all the infrastructure needed for dynamic allocation, filesystem access, user programs, or general device drivers. Adding a call to a hosted function does not magically implement that subsystem.

A good systems-language compiler gradually adds a tested freestanding subset, explicit hardware intrinsics, and ABI tests. Unsupported features should fail clearly instead of silently generating incorrect code.

## Exercise

Run `bash os/build.sh`, then inspect the generated `build/kernel.s`. Find the generated `_start` symbol and compare it with the linker entry. Treat generated assembly as diagnostic output; do not hand-edit it as a lasting fix.

## 7. Trace the actual freestanding call path

A hosted program normally starts through a runtime that prepares arguments, initializes libraries, and eventually calls the program entry point. A freestanding kernel cannot assume that machinery exists. The boot path transfers control into the kernel, and the kernel must initialize the facilities it uses before depending on them.

The VNTOS build invokes the compiler's freestanding backend, assembles its output, and links it with the bootstrap and interrupt objects. This is a different pipeline from compiling a normal VNT application. When a symbol is missing, inspect whether it was generated by the VNT compiler, defined in assembly, or expected from a runtime that the kernel does not link.

## 8. Keep a documented ABI between VNT and assembly

The ABI defines how compiled code and assembly agree on function names, argument registers, saved registers, stack alignment, return values, and symbol naming. A source function named `interrupt_dispatch` is emitted by the current backend under its VNT symbol prefix. The assembly caller must use the emitted symbol, which is why reading `nm build/kernel.elf` is part of debugging.

An ABI assumption that exists only in someone's head is a latent bug. When adding a new assembly entry point, document its symbol name, arguments, registers it changes, stack assumptions, and return behavior. If the compiler's generated prologue changes, revisit any kernel assembly that assumes a particular frame layout.

## 9. Inline assembly limitations are architectural constraints

Inline assembly can execute privileged instructions or access special registers, but the current VNT feature does not expose the full operand-constraint and clobber model of a mature compiler. This makes complex blocks hard to audit: the compiler may not know which registers or flags the assembly modifies.

Use inline assembly only for small, localized operations whose surrounding assumptions are explicit. Keep interrupt frame construction in `os/interrupts.S`, where the exact push/pop sequence and `iretq` are visible. Do not move ordinary command policy, parsing, or driver state machines into assembly.

## 10. Freestanding code needs explicit substitutes

Do not assume a general-purpose allocator, file API, thread API, or process environment exists. A kernel function should use the facilities actually provided by the kernel and should state any memory-size or input-length limits. If a helper depends on the hosted standard library, either replace that dependency with a deliberately small freestanding implementation or leave the helper out of the kernel build.

## Lab: investigate one emitted symbol

Build the kernel, run `nm build/kernel.elf`, and locate the emitted VNT entry and interrupt dispatcher symbols. Compare those names with the source-level function declarations and assembly call sites. Record the mapping and explain how an incorrect symbol name would appear in a linker error.

## 11. Separate compiler bugs from kernel bugs

When a VNT construct fails in the freestanding path, reproduce the smallest example that demonstrates the compiler behavior. If the minimal example fails to parse or type-check, investigate the frontend. If it emits assembly but the assembler rejects it, inspect the emitted instruction syntax. If assembly succeeds but linking fails, inspect symbols and object inclusion. If the ELF links but QEMU fails, move to runtime diagnosis.

This sequence prevents a compiler limitation from being "fixed" by adding arbitrary assembly to the kernel. It also gives you a compact regression test that can be used when the compiler is improved.

## Lab: follow a function end to end

Pick `interrupt_dispatch` or another kernel function. Find its source declaration, the compiler-emitted symbol, the corresponding assembly call site if applicable, and the final ELF symbol. Write one sentence about the contract at each boundary. This is a practical introduction to ABI debugging.

## 12. Make unsupported assumptions visible in reviews

When reviewing a kernel patch, call out dependencies on hosted libraries, dynamic allocation, thread-local state, exceptions, or compiler-generated stack layout. These assumptions may be perfectly normal in an application but invalid in this freestanding environment. Do not silently replace a missing feature with inline assembly unless the replacement has a documented ABI and a regression test.

The goal is to keep the VNT portion readable and testable while isolating the minimum CPU-specific mechanics in assembly. If a proposed change requires a large assembly block for ordinary policy, revisit the boundary before accepting it.

## 13. A kernel function should be easy to audit

Prefer a short VNT function with a named responsibility over a large block that combines register manipulation, parsing, and output. If the function changes global state, name the state and explain the invariant. If it calls assembly, document the emitted symbol and argument contract. If it is called from an IRQ, explain why its execution time and side effects are bounded.

These requirements are practical guardrails while the freestanding compiler and runtime are still evolving. They also make future compiler improvements easier because the source expresses the intended behavior independently of the current backend's quirks.

## 14. Keep interfaces smaller than implementations

A module interface should expose the operations another module needs, not every internal variable or hardware detail. The shell needs a way to print text and read a line; it should not need to know the UART divisor or the PS/2 controller status bits. The interrupt dispatcher needs a narrow way to update timer state; it should not need to know the shell's command-buffer layout.

This separation makes refactors safer. When an implementation changes but its contract remains stable, callers should not need unrelated edits. When a caller needs an internal detail, reconsider whether the interface is missing a deliberate operation.
